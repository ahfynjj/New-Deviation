# TX15 MAX 实机记录：2026-09-27

原生 Deviation 路线；允许参考 EdgeTX TX15 的板级适配。本次继续使用 PWLINK2 Lite / CMSIS-DAP、100 kHz SWD 和已有四线连接。

## 首阶段目标

验证按住按钮复位 → 复位捕获暂停 → 调试器设置 PH12 输出高 → 松开按钮仍可访问且 CPU 保持暂停 → 恢复原固件启动。只操作已核实的易失性调试、GPIO 配置，不写入 Flash、选项字、程序计数器或 RAM 程序。

## 首次连接与 10:08 测试

- 首次只读连接 No ACK；用户随后确认刚开机并重新连接。
- 按钮触发后的复位期间，CPUID 可读，但首次向 `DBGMCU_APB3FZ1 (0x5C001034)` 写看门狗暂停位时返回 FAULT ACK。写入是否生效不能仅凭异常确定。
- 此时尚未执行复位捕获设置或 GPIO 写入，不能声称 CPU 已暂停。
- finally 释放 NRST、恢复原调试寄存器并允许 CPU 运行；读回原应用状态：`DHCSR=0x03010000`、`VTOR=0x20000000`、`RCC_CFGR=0x1B`，PH12 输出高。用户确认屏幕恢复正常。
- 无 Flash/RAM 程序下载。日志：`local/reset-halt-power-20260927-100822.json`。

## 调整后的测试顺序

参考已安装 pyOCD 0.45.1 的 STM32H750 `safe_reset_and_halt()`：复位期间只操作核心 DEMCR/DHCSR，释放复位后才访问外设寄存器。移除导致上次 FAULT 的复位期间看门狗寄存器访问。

捕获成功后，先打开 GPIOH 时钟、通过 BSRR 预置 PH12 高、再设置推挽输出；恢复 PA4 上拉输入以识别松手。设置并读回看门狗调试冻结位，限定等待松手时间，随后自动恢复原固件。所有目标地址写入采用白名单并记录完成状态。

ST 寄存器依据：[STM32H750 CMSIS 头文件](https://github.com/STMicroelectronics/cmsis-device-h7/blob/master/Include/stm32h750xx.h)。`DBGMCU_APB3FZ1` 偏移 0x34 的 bit 6 对应 WWDG1，`APB4FZ1` 偏移 0x54 的 bit 18 对应 IWDG1。

脚本：`local/hardware-session/reset-halt-power.py --arm`，显式 --arm 才访问设备；语法编译通过不代表实机步骤成功。脚本处于本地 bench 区，不是可对未知硬件使用的通用工具。

## 10:10 调整后测试等待超时

调整后脚本已连接并等待 120 秒，未检测到按钮低电平。`reset_attempted=false`，`writes=[]`，因此该修订尚未经过复位实测，不能声称总线访问错误已修复。日志：`local/reset-halt-power-20260927-101056.json`。进程已退出，没有保持复位或暂停 CPU。

## 10:17 复位暂停与松手后的电源保持通过

调整后的顺序通过：复位期间只设置 DEMCR/DHCSR，释放后成功捕获，配置 PH12 推挽高和 PA4 上拉输入。检测到按钮松开后再等待 1 秒，核心仍暂停且 SWD 可读：

- `DHCSR=0x00030003`：S_HALT=1，调试开启。
- `VTOR=0x08000000`、`RCC_CR=0x4025`、`RCC_CFGR=0`、`RCC_D1CFGR=0`。
- `SCB_CCR=0x40200`、`MPU_CTRL=0`：I/D cache 与 MPU 未开启。
- `GPIOH_MODER=0xFDFFFFFF`、`GPIOH_IDR=0x1000`、`GPIOH_ODR=0x1000`；PH12 输出高。
- `GPIOA_IDR=0xC010`：PA4 高，按钮已经松开。

随后恢复调试寄存器并继续原启动入口，读回运行中的原应用；用户确认屏幕恢复正常。日志：`local/reset-halt-power-20260927-101742.json`。这证明短时暂停和按钮释放后的调试器电源保持，不代表原生固件已实现自主开关机。

## 10:22 首次 RAM 诊断实机执行通过

重新构建未修改的 `hardware/tx15/ram_probe`，9 项自动检查通过。沿用已验证的复位暂停和 PH12 保持流程：

1. 核对 HSI、分频、cache/MPU、SysTick/异常状态及看门狗软件启动选项；不修改选项字。
2. 读取并保存原复位入口核心上下文，PC=0x0800E058、MSP=0x2001FFF0，与内部 Flash 向量相符。
3. ELF 地址检查和 ELF/BIN 固定 SHA256 校验通过；将 1292 字节镜像补齐至 1296 字节，以连续对齐 32 位 SWD 写覆盖完整 AXI 双字，再清零 80 字节 mailbox。镜像和 mailbox 均逐字节回读一致。
4. 设置特权 Thread/MSP、屏蔽中断、Thumb 状态和 RAM 入口，运行已有启动代码。代码用 STRD 初始化栈、BSS 和 mailbox，执行 scratch 检查及 SysTick/主循环。
5. 同一运行中直接从设备读取两份 80 字节 mailbox，中间约 0.3 秒；两份状态均为 3，error=0，ram_words=512，无记录的异常。

两个计数器均前进，证明实际执行了测试程序、SysTick 中断和主循环。验证范围为诊断程序自用的 2 KiB scratch，不是全部片内 RAM 或 SDRAM。

测试结束暂停 CPU，关闭/清理测试 SysTick，恢复 VTOR 和保存的完整核心上下文，逐寄存器回读核对后继续原启动入口。`context_restored=true`，cleanup_errors 为空；读回 `DHCSR=0x01010000`、`VTOR=0x20000000` 和原时钟/cache/MPU 状态，用户确认屏幕恢复正常。没有写入内部/外部 Flash、选项字或射频控制引脚。
