## 访问方式与结果

工具：项目独立环境 `tools/pyocd-venv`，pyOCD 0.45.1，SWD 100 kHz。
使用 generic Cortex-M 会话且 `init_board=False`，只初始化 DP/AP 传输。
未调用目标初始化、自动解锁、核心 halt/reset、程序下载或擦除；读后关闭探针连接。
DP/AP 的协议、调试电源请求和访问地址寄存器有必要设置，因此这里的“读取”不表示 SWD 总线上完全没有写事务。

| DPIDR | 0x6BA02477 |
| AP0 IDR | 0x84770001 |
| CPUID | 0x411FC271 |

| DHCSR | 0x03010000 |
| VTOR | 0x20000000 |

CPUID 对应 Cortex-M7 r1p1；DHCSR 的 S_HALT 为 0，读取时核心未暂停。
DBGMCU 的 DEV_ID=0x450、REV_ID=0x2003，对应 H742/H743/H753/H750 家族及 V 修订，不能仅凭该值区分 H750 完整型号。
依据：[ST RM0433](https://www.st.com/resource/en/reference_manual/rm0433-stm32h742-stm32h743753-and-stm32h750-value-line-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)。

当前系统时钟选择 PLL1，I/D cache 和 MPU 已开启，向量表位于 0x20000000。
这些是正在运行的应用状态，**不符合 RAM 诊断要求的 reset-halt 前提**。

原始 JSON 保存在本地 `local/identity-20260926-190522.json`；读取脚本位于 `local/hardware-session/identify.py`。
首次操作只证明一次低速 SWD 读访问成功；后续备份结果见下。

## 19:10 电子容量核对与内部 Flash 备份

用户反馈拍 MCU 需要拆主板，故不要求为基础联调拆板；以电子身份和资源寄存器核对可用的芯片公共资源。封装/完整料号仍未确认，不以软件读值冒充丝印确认。

- `0x1FF1E880` 读取为 `0x00000080`，低 16 位表示 128 KiB 内部 Flash。
- `FLASH_OPTSR_CUR=0x1BC6AAF0`，RDP 字段为 `0xAA`；未解锁或改动选项字节。
- Cortex-M7 / DEV_ID=0x450 / 128 KiB 与 STM32H750xB 配置相符，可作为后续公共片内 RAM 诊断的工作依据。具体外设引脚仍需板级验证。
- 通过相同的 DP/AP 路径读取 `0x08000000..0x0801FFFF` 两遍，各 131072 字节，逐字节一致。未调用 Flash 算法，也未分析现有应用实现。
- 两份 SHA256：`984420d754587cd5561c1b3f3df49ccdd34da868ff785efbdcdc0cff09569ad0`。
- 本地保存位置：`local/backups/tx15-20260926-191005/`，含两份 BIN 和 `manifest.json`；不提交备份固件到 Git。
- 这是所报告容量范围的内部 Flash 备份，**不包含外部 Flash、SD 卡等数据，也不是已验证的整机恢复包**。
- 未暂停/复位核心，未装载 RAM 程序；NRST 动作和复位供电保持仍未测试。

容量依据：[ST RM0433 电子签名章节](https://www.st.com/resource/en/reference_manual/rm0433-stm32h742-stm32h743753-and-stm32h750-value-line-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)、[STM32H750 官方资源说明](https://www.st.com/en/microcontrollers-microprocessors/stm32h750-value-line.html)。
