# New Deviation TX15 快速推进实施计划

> **For agentic workers:** Use superpowers:executing-plans for inline execution. 按用户要求控制 token 消耗，不默认启用多代理；每阶段围绕一个实机可见成果，阶段完成才提交一次代码与简短记录。

**Goal:** 尽快在 TX15 MAX 上显示并操作原生 Deviation，随后打通摇杆→混控→ELRS 接收端的链路。

**Architecture:** 保留 Deviation 页面、模型和混控核心，仅新增 TX15 平台适配。沿用已验证的电源、PLL128、SDRAM 和 RAM 装载路径。硬件参考可查 EdgeTX 板级代码，但不采用其应用框架。

**Tech Stack:** 原工程 C、STM32H750、LTDC/面板控制接口、SDRAM、现有 Arm GCC、PWLINK2/CMSIS-DAP、CRSF。

**Spec:** `docs/superpowers/specs/2026-09-21-tx15-native-design.md`。本计划依据用户 2026-09-28 对速度/token 成本的要求，覆盖旧计划的执行顺序；继续遵守原生 Deviation、实机优先。后续明确允许的板级参考优先于旧设计中的历史禁止条目。

## 当前起点与边界

- 已实测：原生电源保持、RAM 代码运行、HSE、PLL128、SDRAM 前 64 KiB及恢复原固件。
- 未完成：原生屏幕、实际输入、板上 Deviation 应用、ELRS 链路、独立启动。
- 只做支持下一项功能必需的底层工作。全容量/长时间内存测试、最高主频、通用装载器重构暂缓。
- 保留镜像核对、写入范围限制、异常退出恢复，停止为已稳定的底层能力反复做同类实测。
- 此计划不自动启动硬件操作。实施时仍在脚本 ARMED 后才提示用户按键。

## P0：下一轮直接执行的任务

### 文件职责

- 新建 `hardware/tx15/board/display.c`、`display.h`：面板控制、LTDC 配置及背光；不承担页面逻辑。
- 新建 `hardware/tx15/display_demo/main.c`、`display.ld`：测试画面及受限内存布局，与已验证的诊断入口分开。
- 新建 `utils/build-tx15-display.ps1`：复用现有编译环境，生成屏幕演示 ELF/BIN。
- 调整本地 `local/hardware-session/ram_session.py`：增加明确的屏幕演示装载/退出分支，保持原诊断可用。需要恢复的 LCD/背光/时钟状态纳入退出流程。
- 复用 `hardware/tx15/board/power.c`、`clock.c`、`pll.c`；SDRAM 初始化从 `sdram.c` 中最小拆出，避免每次启动都跑完整诊断。
- 仅针对新增的地址边界、显示时序计算或恢复错误分支补自动检查；不新建通用测试框架。

### 执行步骤

- [ ] 一次性核对本机面板尺寸、控制接口、RGB/LTDC 引脚、背光和像素时钟来源，记录必要值。旧资料的 480×320/480×272 不一致须在此解决，不能凭历史宏直接配置。
- [ ] 首选 RGB565 单帧缓冲，实测其实际占用区域后立即用于出图。若确认为 480×320，单缓冲为 307200 字节，按 320 KiB 保留；64 KiB 的旧证据不能代替此检查。
- [ ] 保持已验证 CPU/AHB 档位；只增加显示必需的像素时钟。若带宽不足，先降低刷新率或显示复杂度，不直接展开最高主频优化。
- [ ] 按数据手册/板级参考完成面板初始化、LTDC 和背光；用 CPU 填充单缓冲，暂不引入 DMA2D、双缓冲和动画框架。
- [ ] 画出纯色、边框、New Deviation 字样和递增数字。第一张图有偏移/颜色问题时，只修对应显示参数。
- [ ] 编译及地址检查通过后，合并进行一次实机验收，记录屏幕结果与恢复结果。只有失败或新增风险才重复。
- [ ] 提交本阶段代码，TODO 写三项：已完成、当前阻塞、下一动作。无需每次成功重复扩写多份报告。

### 阻塞处理

- 若屏幕不亮，按背光→面板复位/配置→像素时钟→LTDC/缓冲地址顺序定位。
- 同一假设连续两次验证失败即停下更换假设；给出具体缺失证据，不重复相同刷载/按键流程。
- 若缺少面板型号/接线证据，先完成可独立进行的构建和绘制部分，再明确只请求必要信息。
- P0 验收通过即进入 P1，不追加全 8 MiB、长时间稳定性或冷启动测试作为门槛。

## 控制 token 与工作范围

1. 单代理顺序执行，不默认每个小改动都派审查代理；只对启动、恢复、存储写入等高风险变更集中审查。
2. 每阶段一次构建/相关检查、一次硬件验证为目标；有新修改或故障才重跑对应部分。
3. 只读相关文件和必要日志，不重复扫描仓库、历史记录和已核实手册；不开发模拟器。
4. 功能开发集中成批，提交按可见里程碑；只维护本计划勾选状态与 TODO，原始调试日志留本地。
5. 验收看“屏幕、操作、通道、接收端”四类成果，不把测试数量当作进展指标。
6. 若本轮转为纯底层排障，说明它具体阻塞哪个可见功能及结束条件；没有直接依赖的优化推迟。
